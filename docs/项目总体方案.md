# Zhimo（知墨）跨平台多语种智能输入与语音转录平台——项目总体方案

> 文档状态：架构基线草案 1.0  
> 编制日期：2026-09-02  
> 适用范围：Windows、Linux、macOS、Android、iOS/iPadOS  
> 首发产品：中文拼音 + 英语输入 + 中英语音转文字

## 1. 执行摘要

本项目不应被建设成五个彼此独立的输入法客户端，而应建设成一个“通用输入平台”和基于该平台交付的首款中英文输入法产品。

平台同时接收键盘、触摸、语音等输入信号，通过统一会话、语言引擎、候选排序、个性化学习、隐私策略和跨设备同步，向各操作系统提交文字。中文拼音只是首个语言引擎；后续日语、韩语、越南语、阿拉伯语、印度语系及形码输入法均可复用底座。

项目的最终产品形态包括：

1. 五个平台的系统级输入法。
2. 用于设置、词库、语音模型、备份和设备管理的配套 App。
3. 默认离线运行的通用输入运行时与语言/语音引擎。
4. 用户主动开启的端到端加密同步服务。
5. 面向新语种开发者的 SDK、语言包规范、测试工具和 Input Method Studio。

核心架构结论：

- 使用“轻量嵌入式运行时 + 配套后台服务”的双运行时架构。
- 通用运行时建议以 Rust 实现，对平台和第三方引擎暴露稳定 C ABI。
- 中文首发引擎通过适配器接入 `librime`，但平台公共接口不得依赖拼音或 Rime 私有模型。
- 语音识别通过 `SpeechProvider` 抽象接入本地跨平台引擎、系统引擎和可选云端引擎。
- 首选本地流式 ASR 技术候选为 sherpa-onnx；whisper.cpp 作为离线批量转录及质量基准候选，最终选型由真实设备基准测试决定。
- iOS 第三方键盘扩展无麦克风访问权，必须采用系统听写能力或容器 App 转录等合规降级方案，不能承诺与 Android 完全相同的键盘内录音体验。
- 输入、音频、网络、模型推理和数据同步必须处于不同的线程/进程边界，任何重型任务都不得阻塞按键处理。

## 2. 产品定义

### 2.1 产品愿景

建立一个跨设备、隐私优先、可扩展的个人语言输入系统：既能理解用户的词汇与表达习惯，也能让开发者快速构建其他语种和其他输入方式的系统级输入法。

### 2.2 产品承诺

- 键盘输入和基础语音输入默认可以离线完成。
- 使用时间越长，候选命中率越高、需要的按键和修改越少。
- 中英文可以自然混合，不强迫用户频繁切换模式。
- 用户能够查看、修改、导出和彻底删除个人学习数据。
- 换设备后可选择恢复词库、偏好和模型配置，但不上传完整按键历史。
- 一个新语种主要开发语言规则、模型和布局，不重复实现五个平台接入。

### 2.3 产品边界

项目包括：

- 系统级文字输入。
- 短时语音听写和长音频转录。
- 个人词库、专业词库、语言模型及个性化学习。
- 多设备配置和词库同步。
- 语言包、键盘布局和引擎开发工具。

项目首期不包括：

- 电话通话录音。
- 未经用户明确操作的环境持续监听。
- 默认上传原始音频或完整输入日志。
- 医疗、司法等高风险场景中无需人工校验的权威转录。
- 绕过操作系统安全输入框或第三方键盘限制。

## 3. 最终产品形态

### 3.1 系统输入法

| 平台 | 系统接入 | 主要交互 | 语音形态 |
|---|---|---|---|
| Windows | TSF 输入服务 | 物理键盘、候选窗、托盘设置 | 后台服务采集麦克风，本地/系统/云端 ASR |
| Linux | Fcitx 5，后续 IBus | 物理键盘、候选窗、配置工具 | 用户会话服务采集麦克风，本地 ASR |
| macOS | InputMethodKit | 物理键盘、候选窗、菜单栏 | 配套进程使用 Speech/本地 ASR |
| Android | InputMethodService | 触摸键盘、手势、候选栏 | 键盘内按住说话或点击听写，需录音权限 |
| iOS/iPadOS | Custom Keyboard Extension | 触摸键盘、候选栏 | 第三方键盘不能直接访问麦克风；使用系统听写入口或容器 App 转录 |

### 3.2 配套 App

配套 App 提供：

- 输入法安装引导和权限说明。
- 语言包、词库、语音模型下载与更新。
- 个人词库查看、搜索、编辑、导入和导出。
- 快捷短语、键盘布局、主题、模糊音和双拼配置。
- 隐私模式、应用黑名单和数据保留策略。
- 录音文件转录、转录历史和导出。
- 账户、设备、加密同步和恢复密钥管理。
- 诊断包生成；默认不包含输入正文和原始音频。

### 3.3 开发者产品

- Universal IME Runtime：通用输入运行时。
- Language Engine SDK：语言引擎与语言包 SDK。
- Speech Provider SDK：语音识别、标点、热词和后处理扩展接口。
- Input Method Studio：布局、词典、规则、模型和测试用例的可视化工具。
- Package Registry：签名语言包、词库和模型的发布服务。

## 4. 架构评估与技术决策

### 4.1 候选方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 五个平台独立开发 | 初期单端启动快 | 重复实现、行为不一致、无法复用学习和测试 | 否决 |
| Flutter/React Native 统一实现 | 设置页面复用高 | 无法替代各系统原生 IME 接口，扩展环境限制多 | 仅用于配套 UI |
| 直接以 librime 作为全部底座 | 中文能力成熟 | 公共模型偏向字词转换，难覆盖语音与任意语种 | 作为中文引擎适配器 |
| C++ 统一核心 | 生态成熟、易接 librime/ASR | 常驻系统组件的内存安全和并发风险较高 | 可行备选 |
| Rust 运行时 + C ABI + 原生引擎适配 | 内存安全、跨平台、边界清晰、引擎语言不限 | 构建链和 FFI 治理更复杂 | 推荐 |

### 4.2 推荐技术基线

- 核心语言：Rust stable，固定工具链版本并定期升级。
- 公共二进制接口：C ABI；跨 ABI 只传不透明句柄、定长标量和显式长度缓冲区。
- 序列化：内部配置使用 JSON/YAML；持久化和同步使用带版本的 Protobuf 或等价 schema-first 格式。
- 本地结构化存储：SQLite；高频词典查找使用只读 mmap/FST/Trie 等专用结构。
- 中文引擎：`librime` C API 适配器。
- 本地流式语音候选：sherpa-onnx；离线批处理/对照候选：whisper.cpp。
- 桌面后台通信：本机鉴权 IPC；Windows Named Pipe、Linux Unix Domain Socket、macOS XPC 或 Unix Domain Socket。
- Android：Kotlin + JNI/NDK。
- Apple：Swift/Objective-C + C ABI 静态库/XCFramework。
- Windows：C++/WinRT TSF 外壳 + Rust 核心动态库/静态库。
- Linux：Fcitx 5 插件优先，IBus 适配器后续交付。

### 4.3 关键原则

1. 平台层不包含语言转换逻辑。
2. 语言引擎不直接操作窗口、麦克风或网络。
3. 公共类型不出现 `pinyin`、`hanzi` 等语种专属概念。
4. 基础输入不依赖账户、网络或后台服务。
5. 输入线程不进行网络、磁盘维护、模型加载或长耗时推理。
6. 语音只是另一种输入源，不与某个语言引擎绑定。
7. 同步传输稳定逻辑记录，不复制引擎私有数据库文件。
8. 所有学习都可关闭、解释、撤销、导出和清除。
9. 平台能力通过 capability 协商，允许显式降级。
10. 插件、模型和语言包必须签名并声明许可证、权限和资源需求。

## 6. 通用输入底座

### 6.1 统一事件

```rust
pub enum InputEvent {
    Key(KeyEvent),
    Text(TextInput),
    SpeechPartial(SpeechHypothesis),
    SpeechFinal(SpeechHypothesis),
    SelectCandidate(CandidateId),
    MoveCursor(CursorMove),
    Delete(DeleteUnit),
    SwitchProfile(ProfileId),
    Reset(ResetReason),
}
```

事件模型必须覆盖物理键盘、触摸、滑行、语音、手写和无障碍设备。平台特有键码在进入运行时前规范化；原始平台数据仅保留在可选扩展字段中。

### 6.2 会话与组合状态

每个焦点文本框对应一个隔离会话：

```text
InputSession
├── session_id
├── input_scope
├── language_profile
├── composition
├── selection
├── candidates
├── surrounding_context
├── privacy_policy
└── engine_states
```

`Composition` 由通用 Segment 组成，可表达中文拼音片段、日语文节、韩文音节、越南语重写区间和语音临时结果。所有状态转换应尽量确定性，使同一事件序列可在测试环境完整回放。

### 6.3 引擎契约

```rust
pub trait InputEngine {
    fn metadata(&self) -> EngineMetadata;
    fn capabilities(&self) -> EngineCapabilities;
    fn create_session(&self, config: SessionConfig) -> EngineSessionHandle;
    fn process(
        &self,
        session: EngineSessionHandle,
        event: &InputEvent,
        context: &InputContext,
    ) -> ActionBatch;
    fn apply_feedback(&self, event: &FeedbackEvent);
    fn flush(&self) -> Result<(), EngineError>;
}
```

引擎返回动作，不直接调用平台：

- `UpdateComposition`
- `ShowCandidates`
- `CommitText`
- `DeleteSurroundingText`
- `MoveCursor`
- `RequestLayout`
- `PlayFeedback`
- `CloseComposition`

### 6.4 候选统一模型

候选至少包含：

- 稳定会话内 ID。
- 展示文本和实际提交文本。
- 语言、脚本和方向。
- 来源引擎与候选类型。
- 引擎原始分数和统一重排分数。
- 匹配区间、替换区间和组合分段。
- 置信度、注释和可解释原因。
- 是否允许学习、同步和云端处理。

### 6.5 多语种路由

语言路由器根据用户模式、字符脚本、文本框类型和有限上下文选择引擎，并可以合并多个引擎的候选。它必须保护：

- URL、邮箱、文件路径。
- 代码标识符、命令行和版本号。
- 人名、品牌名和用户固定词。
- 从右向左文本和混合方向文本。
- Unicode 字素簇、组合字符和 emoji 序列。

文本删除、光标移动和长度计算应以字素簇或平台规定的 UTF-16 单元正确转换，不能直接按 UTF-8 字节处理。

## 7. 语音转文字底座

### 7.1 两类语音产品场景

**即时听写**：用户在输入法中按住或点击麦克风，实时看到临时结果，松开后提交到当前文本框。目标是低首字延迟、可撤销和不中断键盘输入。

**长音频转录**：用户在配套 App 中录音或导入文件，获得带时间戳、分段、可选说话人和导出能力的全文。目标是准确率、稳定性和断点恢复。

二者共享模型管理、ASR Provider、标点、热词和隐私组件，但使用不同的会话、资源配额和 UX，不应强行复用同一处理管线。

### 7.2 语音处理管线

```text
Microphone / Audio File
        │
        ▼
Audio Capture → Resample/Channel Mix → Noise Policy
        │
        ▼
VAD / Endpointing → Streaming Buffer → ASR Provider
        │                              │
        │                         Partial / Final
        ▼                              ▼
Language ID → Punctuation → ITN → Custom Vocabulary
        │
        ▼
Text Normalization → Candidate/Composition → User Confirm → Commit
```

其中 ITN（Inverse Text Normalization）负责把“二零二六年九月二日”“百分之三点五”等口语形式转换为适合书写的日期、数字、货币和单位。

### 7.3 Speech Provider 契约

```rust
pub trait SpeechProvider {
    fn metadata(&self) -> SpeechProviderMetadata;
    fn capabilities(&self) -> SpeechCapabilities;
    fn prepare(&self, request: PrepareRequest) -> PrepareStatus;
    fn start_stream(&self, config: SpeechSessionConfig) -> SpeechSessionHandle;
    fn push_audio(&self, session: SpeechSessionHandle, frame: AudioFrame);
    fn poll(&self, session: SpeechSessionHandle) -> Vec<SpeechEvent>;
    fn finish(&self, session: SpeechSessionHandle);
    fn cancel(&self, session: SpeechSessionHandle);
}
```

Provider 可实现为：

- 跨平台本地 ASR。
- 操作系统语音 API。
- 企业内网 ASR。
- 用户明确授权的云端 ASR。

运行时根据离线要求、语言、设备性能、模型可用性、成本和隐私策略选择 Provider。云端 Provider 不得成为基础输入的唯一实现。

### 7.4 初步引擎评估

**sherpa-onnx**：支持本地流式和非流式识别、VAD、标点及多平台/多语言绑定，较适合作为首个跨平台流式 Provider。风险是模型组合和质量差异大，需要建立自有模型清单、许可证核验和基准体系。

**whisper.cpp**：平台覆盖广，离线和量化能力成熟，适合长音频转录、离线高质量模式以及交叉验证。其流式方式和端点体验需在移动设备上实测，不预设为即时听写唯一方案。

**系统 API**：安装体积可能更小，能利用系统专有加速，但平台版本、语言支持、是否联网和行为一致性不可控。作为可选 Provider 和降级能力，不作为统一语义基线。

最终选型必须用同一测试集比较：

- 中文普通话、英文和中英混说字/词错误率。
- 首个临时结果、首个稳定结果、最终结果延迟。
- 实时率、峰值内存、模型体积、耗电和发热。
- 低端 Android、无 NPU Windows、Intel/Apple Silicon macOS 的表现。
- 噪声、远场、口音、专有名词和数字标点准确率。
- 模型及训练数据许可证能否用于目标商业模式。

### 7.5 热词与个性化

个人词库可以向 ASR 提供热词，但必须通过中间层映射，避免绑定某个引擎的私有格式：

```text
VoiceLexiconEntry
├── written_form
├── spoken_forms[]
├── language
├── boost
├── domain
├── expiry
└── privacy_scope
```

拼音输入学到的项目名、人名和专业词可以在本地成为语音热词；语音确认过的新词也可以建议加入个人词库。原始音频默认不进入长期学习。

### 7.6 iOS 特殊边界

Apple 官方文档明确说明 Custom Keyboard Extension 没有麦克风和扬声器访问能力。因此：

- iOS 键盘扩展中不得直接启动自有录音。
- 可正确声明 `hasDictationKey`，与系统可能呈现的听写入口协同，但它不授予扩展麦克风权限。
- 配套 App 可以在用户授权后使用 Apple Speech 或本地 ASR 完成录音/文件转录。
- 可提供“在配套 App 中听写并复制/分享”的降级流程。
- 是否能从当前第三方应用无缝跳转、返回并插入文本，必须以当期 iOS 审核规则和真机行为为准，不能成为核心承诺。

这属于平台能力差异，不应通过私有 API 或误导性权限说明规避。

## 8. 个性化学习与排序

### 8.1 学习层级

- 即时记忆：短时间提升刚使用词汇的权重。
- 长期偏好：按提交频率与时间衰减调整。
- 上下文学习：学习相邻词、输入场景和语言切换习惯。
- 自动造词：发现稳定组合，达到阈值后建议或加入用户词库。
- 负反馈：删除、撤销、立即改写和跳过首选均影响排序。
- 语音反馈：只使用用户确认后的最终文字，不用未确认临时结果学习。

### 8.2 数据最小化

优先保存“输入签名、选中词条、聚合计数和上下文特征”，而不是完整句子。学习记录带有：

- 语言和引擎版本。
- 来源设备和逻辑时间。
- 隐私范围和同步策略。
- 过期/衰减参数。
- 删除墓碑。

密码框、安全输入、无痕模式和用户配置的禁用应用中不学习。语音原始音频默认会话结束即释放；用户主动保存的录音进入独立加密存储域。

## 9. 数据与同步架构

### 9.1 数据域

| 数据域 | 示例 | 默认同步 |
|---|---|---|
| SystemLexicon | 基础语言词库 | 否，由包管理更新 |
| UserLexicon | 用户明确添加词条 | 是，可关闭 |
| LearnedLexicon | 自动学习词频 | 是，可关闭 |
| DomainLexicon | 医学、编程等词库 | 同步安装清单 |
| Settings | 双拼、主题、布局 | 是，可分平台覆盖 |
| SpeechModels | ASR 模型文件 | 否，同步模型标识 |
| SavedRecordings | 用户保存录音 | 默认否 |
| Transcripts | 长音频转录结果 | 默认本地，可选择同步 |
| Tombstones | 删除记录 | 是 |

### 9.2 同步原则

- 客户端加密后上传；服务端不持有明文密钥。
- 使用稳定逻辑记录和 schema version，不上传 SQLite/LevelDB 私有文件。
- 使用操作日志或等价的可合并结构处理多设备离线冲突。
- 删除产生墓碑并保留有限时间，防止旧设备把已删词重新带回。
- 恢复密钥丢失时，服务方不能承诺恢复明文数据。
- 同步与账户完全可选；本地导出是独立能力。

## 10. 安全、隐私与合规

### 10.1 威胁重点

- 输入法进程被利用读取用户输入。
- 语言包、模型或更新渠道被投毒。
- IPC 被其他本地进程伪造或窃听。
- 崩溃日志意外包含输入正文。
- 云端语音误上传或超期保存。
- 跨设备删除不完整。
- 第三方插件越权访问网络、文件或上下文。

### 10.2 控制措施

- 发布物、包、词库和模型使用签名清单及哈希校验。
- 原生第三方插件初期不开放动态加载；社区插件优先采用受限 DSL/WASM，并按平台政策裁剪。
- IPC 使用每用户端点、操作系统 ACL、握手令牌和协议版本校验。
- 日志字段白名单化，正文和音频禁止默认进入日志。
- 密钥进入 Keychain、Android Keystore、Windows Credential/DPAPI 或 Linux Secret Service。
- 安全输入场景强制关闭学习、上下文读取、剪贴板和网络功能。
- 云端语音使用明确的按次授权、传输加密、短保留期和删除机制。
- 建立依赖 SBOM、许可证清单、漏洞扫描和可复现构建路线。

## 11. 性能与可靠性目标

以下为架构目标，正式阈值在原型基准后冻结：

| 指标 | 目标方向 |
|---|---|
| 按键事件处理 P95 | 本地轻量路径不超过 10 ms |
| 候选首次展示 P95 | 常用词典已热加载时不超过 30 ms |
| 输入线程网络依赖 | 0 |
| 输入线程动态模型加载 | 0 |
| 崩溃影响 | 单引擎/语音失败不影响原始字母输入和安全退出 |
| 语音首个临时结果 | 以设备档位制定，目标低于 500 ms |
| 语音最终结果 | 端点后尽可能低于 1 s，按模型档位验收 |
| 用户数据持久化 | 崩溃后不损坏已提交词库，支持事务与恢复 |
| 离线能力 | 键盘输入完整可用，本地模型安装后语音可用 |

必须设置资源预算档位：轻量、中等和高质量。运行时根据内存、CPU/NPU、电量和热状态选择模型或提示用户切换，不能静默拖慢整个系统。

## 13. 测试与质量工程

### 13.1 测试层级

- 纯函数单元测试：Unicode、分词、排序、ITN、冲突合并。
- 契约测试：每个文字引擎和 Speech Provider 必须通过同一套行为契约。
- 事件回放：用确定事件序列验证组合、候选和提交。
- Golden 测试：固定词库/模型版本下验证候选和转录结果。
- 模糊测试：随机按键、无效 UTF、损坏词库、乱序 IPC。
- 集成测试：每个平台与真实文本框、浏览器、办公软件、终端的交互。
- 性能测试：冷启动、热路径、内存、耗电、模型切换和长时间运行。
- 安全测试：包签名、IPC、权限、敏感日志和数据删除。

### 13.2 语音质量集

建立获得合法授权的内部评测集，并按以下标签分层：

- 普通话、英语、中英混说和未来目标语种。
- 安静、街道、车内、会议室、远场。
- 不同年龄、性别、地区口音和语速。
- 人名、地名、品牌、技术词和数字单位。
- 1～15 秒听写与 30～120 分钟长音频。

评估至少包含 WER/CER、标点准确率、ITN 准确率、热词召回、延迟、实时率和资源消耗。数据集必须记录来源、授权、用途范围和删除策略。

## 14. 交付路线

路线以“架构闸门 + 可运行产品”推进，不以一次完成五端为前提。

### 阶段 0：技术验证与架构冻结

交付：

- Rust Runtime 最小事件循环和 C ABI。
- Latin/Test Engine 两个参考引擎。
- librime 适配验证。
- sherpa-onnx、whisper.cpp 和至少一个系统 ASR 的真实设备基准。
- Windows TSF、Android IME、iOS Keyboard 的最小平台探针。
- Unicode、数据 schema、隐私边界和 ADR 基线。

退出条件：同一事件测试可以在两种平台壳运行；语音选型有可复现数据；iOS 降级交互获得确认。

### 阶段 1：共享核心与首个闭环

交付：

- 中文拼音、英文直输、中英文切换和候选。
- 用户词频与负反馈基础版。
- Android 或 Windows 其中一个产品化端，另一个验证端。
- 本地短语音听写、临时结果、最终提交和撤销。
- 语言包、模型包的签名和版本机制。

退出条件：核心输入和语音全程离线可用；失败可退回原始输入；不阻塞输入线程。

### 阶段 2：双端正式产品

交付：

- Android + Windows 正式版本。
- 中英文混输、整句、模糊音、热词联动。
- 配套设置 App、词库导入导出、模型管理。
- 加密同步最小闭环。
- 长音频转录基础版。

### 阶段 3：Apple 与 Linux 覆盖

交付：

- macOS InputMethodKit。
- iOS/iPadOS 键盘与容器 App；明确语音降级体验。
- Linux Fcitx 5；随后 IBus。
- 多设备冲突、删除墓碑和数据迁移。

### 阶段 4：智能化与平台化

交付：

- 端侧候选重排、上下文预测和场景化学习。
- 语音自动标点、ITN、语言识别和可选说话人能力。
- Language Engine SDK、Speech Provider SDK 和 Studio。
- 第二个非中文转换型语言作为底座验收；建议选择日语或越南语，以暴露组合模型偏差。

### 阶段 5：生态与企业能力

交付：

- 签名语言包与词库市场。
- 企业内网同步、私有词库、私有 ASR Provider 和集中策略。
- 插件沙箱、权限审计、兼容性认证和长期 API 支持策略。

## 15. 团队与治理建议

最小核心团队应覆盖以下责任，不建议由一个“跨平台客户端组”笼统承担：

- 平台架构与 Runtime/FFI。
- 中文/多语种输入算法。
- ASR、音频和端侧推理。
- Windows/Linux 桌面输入法。
- Apple 平台。
- Android 平台。
- 数据、同步和密码学工程。
- 测试、性能、发布与供应链安全。
- 产品设计、语言资源与隐私合规。

治理方式：

- 重大决定写入 `docs/adr/`，包含背景、方案、结论和后果。
- C ABI、持久化 schema、同步协议和语言包格式执行语义化版本。
- 每次发布生成 SBOM、许可证报告、签名清单和数据迁移报告。
- 平台端不得绕过 Runtime 私自保存用户学习数据。
- 新能力先声明隐私和资源预算，再进入开发。

## 16. 主要风险及缓解

| 风险 | 影响 | 缓解方案 |
|---|---|---|
| iOS 键盘无麦克风权限 | 无法提供键盘内自有录音 | 系统听写协同、容器 App 转录、产品文案明确差异 |
| 通用抽象过度设计 | 首发延迟 | 只抽象已被首发 + 第二语言/第二 Provider 验证的能力 |
| Rust/C++/Swift/Kotlin 多语言构建复杂 | CI 和排错成本高 | C ABI 单边界、生成绑定、固定工具链、契约测试 |
| librime 数据模型渗透公共层 | 未来语种受限 | 严格 Adapter，公共 Candidate/Composition 自主定义 |
| ASR 模型体积和功耗过高 | 移动体验差 | 模型档位、按需下载、VAD、硬件基准和资源治理 |
| 语音/输入数据隐私争议 | 信任和合规风险 | 默认离线、最小采集、显式同意、端到端加密、可审计 |
| 多设备学习冲突 | 候选反复、删除复活 | 逻辑记录、设备时钟、墓碑、幂等合并和迁移测试 |
| 第三方词库/模型许可证不清 | 无法商业发布 | 包级许可证清单、来源证明、发布闸门 |
| 平台 API 和商店政策变化 | 某端功能退化 | capability 协商、系统 Provider、年度兼容审计 |
| “AI 功能”阻塞基础输入 | 卡顿和不可用 | 推理隔离、超时、熔断、原始输入兜底 |

## 17. 成功指标与验收

### 17.1 输入体验

- 首选候选命中率。
- 每个提交汉字的平均按键数。
- 翻页率、撤销率和提交后立即修改率。
- 中英文手动切换次数。
- 按键至候选延迟和崩溃率。
- 使用 7/30/90 天后相对于首次使用的效率提升。

### 17.2 语音体验

- 中文 CER、英文 WER 和中英混说错误率。
- 首个临时结果与最终结果延迟。
- 自动标点、数字日期 ITN 和热词召回率。
- 实时率、峰值内存、耗电和模型下载完成率。
- 用户手动修改比例和整段撤销比例。

### 17.3 平台能力

- 同一语言包在各平台的契约通过率。
- 新语言引擎接入所需平台专属代码量。
- 数据迁移和多设备收敛成功率。
- 离线功能完整率。
- 安全输入场景零学习、零网络的自动验证结果。

最终核心指标定义为：用户使用三个月后，相比第一天少按多少键、少修改多少次，以及语音结果需要修改多少比例。
